date: 2026-10-03 · for: Emerson / Claude · written by Relay 33 (hey)

## Try this (on your PS5 pad)
1. Settings > Controls > Rumble: **your saved settings have Rumble switched off** (`enabled=false` in the game's settings.cfg, last written 11:34 today). If that was your workaround for the stuck buzz, switch it back on, then press "Test rumble".
2. Hold a skid (brake trigger at speed), hold the wire taut, hold a jump charge, then **pause with Esc mid-skid and mid-wire-pull**: the pad must go quiet within a few frames of the pause (before: it kept buzzing, nothing was left to stop it). Also let go, die, or quit to the menu mid-wire: quiet at once / within a quarter second.
3. Fire the main gun and check that the kick lands with the shot, not a beat after. If a held rumble (wire tension, skid) feels pulsed instead of steady, tell me: the pad now gets a fresh 0.25-0.4 s effect about every 0.2 s instead of one endless effect, and that is the one thing I could not feel from here.

## What was wrong (read from the code, then proven by the tests below)
- **Every start used duration 0 = "vibrate until told to stop".** Anything that dropped the stop (a hitch, the game freezing, a crash) left the motors on indefinitely.
- **Loops were edge-triggered**: skid, jump_charge and grapple_tension started on one call and ended on another. Nothing ended them if the mech died or was freed, the anchor was freed, the game paused (`Rumble` runs while paused, the mech does not) or the setting was turned off mid-loop (steps were frozen at the old scale).
- **A play() took effect a frame late**: the Rumble autoload processes before the mech, so an event raised in the mech's frame waited for the next one (about 8-30 ms at the game's frame rates, more under fire).

## What changed (`scripts/core/rumble.gd`, `data/rumble.json`)
- Every effect sent to the pad is finite: time to the next change (at least 0.15 s, at most 0.3 s) plus 0.1 s slack. It is refreshed shortly before it runs out, and only when the value is unchanged or changed, never every frame.
- A loop lives only while its cause calls `Rumble.play(event)` every frame (hold_ms, default 250). Freed mech, released wire, missed stop: it lapses by itself. Hard ceiling `max_s` per loop (skid 12 s, jump charge 4 s, wire tension 40 s, default 30): past it the motors go quiet even if the owner is still asking.
- Loops are dropped on pause and ignored while paused (menu ticks and the Test rumble button still play); everything stops on window focus loss, close request and exit. `stop_all()` is immediate (quit to menu uses it).
- play() and stop() are flushed at the end of the same frame.
- Call sites: skid and jump charge now refresh every frame (`standin_mech.gd`), wire tension no longer guards on is_playing (`wire_anchor.gd`, it went in with Tetsu's 9517bc3).
- Test hook: `Rumble.test_pads` + `Rumble.record` give a timestamped start/stop log instead of calling Input.

## Review (Opus, 2026-10-03)
Relay 35 reviewed fec6d04 (rumble.gd, rumble.json, standin_mech.gd) and the wire_anchor callers. It did not redo the work.

**Checked, and fine (read from the code; the * ones are also covered by tests):**
- Pause*: loops are dropped in `_advance` and play() ignores them while paused. One-shots (finite) and menu ticks still play.
- Scene change and quitting to the menu*: `Game._leave_level` calls stop_all(). Any other scene swap ends loops within hold (0.25 s) and one-shots within their own length.
- Mech death or free*, anchor freed, wire released or snapped: the cause stops refreshing, so the loop lapses 0.25 s later. release() and the slack branch also stop it at once.
- Turning the setting off mid-loop*: steps are rescaled every 0.2 s and a value of 0 sends a stop.
- Pad unplugged and plugged back: `joy_connection_changed` zeroes `_sent_until`, so the next flush re-sends to every connected pad. Two pads: every send goes to all pads, and each send is finite.
- Refresh scheme*: there is one vibration slot per pad, so a new start replaces the old one and nothing piles up. A held loop with the same value is re-sent only when under 0.06 s of the 0.25-0.4 s effect is left (4-7 sends a second), never every frame. A re-send covers the old effect before it ends, so in theory there is no gap.
- "A frame late" fix: there is no double fire. play() queues one deferred flush. The next `_process` flush sees the same value with time left and sends nothing. `_queued` stops a second deferred flush being queued, and re-firing a one-shot restarts its entry instead of adding one. The test confirms one start per step (fire_main: 3).

**Found and fixed (one real bug):** window focus loss only silenced the pad for one frame. stop_all() cleared the loops, but the game keeps running when unfocused, so the skid, wire or jump-charge owner called play() again on the next frame and the pad buzzed in the background. Rumble now holds a `_focused` flag: while unfocused nothing reaches the pad, and on focus in it re-sends at once. Red test first: `test_losing_window_focus_keeps_the_pad_quiet_while_the_cause_goes_on` failed with 2 starts while unfocused and now passes. Assumption: rumble is always silent while unfocused (it does not follow `audio.mute_unfocused`), because a background game should never shake the pad. Commit: "R2 review: losing window focus…".

**Still only reasoned (needs your DualSense):**
- Whether the 0.2 s re-send of the same value can be felt as a pulse. Godot on Linux removes the old force-feedback effect and uploads the new one, which leaves a microsecond gap. The pad's driver may still restart its envelope.
