Why the boss is not a Claude session: a Claude session can start other
sessions (it did, via `claude -p` and crew helpers), but it cannot wake itself
without a prompt, it costs tokens every time it checks in, its context grows
all day (this is what made `/pace` 45 percent of his usage, see memory
`dont-use-pace-skill`), and it cannot change its own account when it runs
out. A Python loop costs nothing to wait and never runs out.

## What to build: `~/Forge/apps/relay` (port 8463, free on 2026-09-29)

A normal Forge app (FastAPI + `static/`, own `.venv`, `forge_app.json` with
a manifest like `apps/crewroom/forge_app.json`), plus a boss process that
runs whether the hub is open or not.

### 1. The boss (`boss.py`, a systemd user service that starts at login)

One tick every 60 seconds, no tokens spent unless it launches something:

1. **Read state from disk only**: goals, tasks, running sessions (saved
   PIDs), the settings file. Everything the boss knows lives in files, so a
   crash or reboot loses nothing.
2. **Read the meters** with `python3 ~/.claude/tools/usage.py --all --json`
   (reuse it, do not copy it; cache for 3 minutes so the usage endpoint is
   not hammered). Accounts come from `~/.local/share/forge/claude/profiles.json`
   plus the default `~/.claude`.
3. **Check the machine** before launching: free disk, load average, and
   whether Jan or a render is busy (memory `local-compute-contention`; Jan
   is shared, never touch it). Too busy means wait, not launch.
4. **Pick the account** by Emerson's rules:
   - never launch on an account at or over 95 percent of its 5-hour window
     or 99 percent of its weekly one (memory `stop-at-95-percent-of-usage-limit`)
   - from 70 percent, at most one launch per account every 15 minutes; from
     92 percent, no new launches on it (memory `usage-pacing-rule`)
   - a resumed task prefers the account it ran on if that account is still
     under the limit and it ended under an hour ago (its prompt cache is
     still warm, so the restart is cheaper)
   - otherwise the account with the most headroom
5. **Pick effort** from the task's priority: `important` = max, the rest
   medium (memory `switch-to-second-subscription-when-out`).
6. **Launch** one task per session, headless:
   `CLAUDE_CONFIG_DIR=<profile> claude -p --output-format stream-json
   --verbose --permission-mode bypassPermissions --effort <e> --session-id
   <uuid>` with the prompt on stdin, in the task's folder. Borrow the shape
   of `apps/crewroom/launch.py` `task_command`; if both need it, move it to
   `~/Forge/shared/claude_launch.py` and have Crew Room import it (shared
   files over duplicated code). Save the PID; stop only by that PID.
7. **Watch** each running session's stream: last activity, tokens, the
   final `result` event. No output for 20 minutes = stuck: stop it by PID,
   mark the task for retry.
8. **Hand over**: when a session exits, read its task file's State. `done`
   goes to the goal's check (below). Anything else is requeued with a resume
   prompt ("read your brief's State and carry on") on the next account the
   rules pick. A task that fails or stalls twice is parked and emailed
   to Emerson instead of looping and burning tokens.
9. **Keep the laptop awake** while anything is queued or running
   (`systemd-inhibit --what=sleep:idle`), and let it sleep when the queue
   is empty. Do not touch the Power app's CPU caps (memory
   `laptop-power-tuning-is-deliberate`).
10. **Tell the other sessions**: post starts and finishes on the crew
    `forge` board, so interactive sessions know what Relay is editing.

### 2. Goals (the "goals thing")

- A goal is one file in the Relay data folder: `goals/<slug>.md` with
  front matter: title, priority, folder, `check` (a shell command that proves
  progress, e.g. `pytest -q`, or "boots in QEMU"), and a short progress log
  the boss appends to.
- Tasks are files in `tasks/<goal>/<nn>-<slug>.md`: what to do, done-when,
  and a State section the session keeps current (the same format as these
  session briefs).
- **Planning turn**: when a goal has no queued tasks, the boss launches one
  short, medium-effort session that reads the goal, its log and the last
  check result, and writes the next 1 to 3 task files, then stops. This is
  the only "thinking boss" and it costs one small session, not a day of
  polling.
- **A goal is only marked done when its `check` command passes**, run by the
  boss itself, not when a session says so. Each finished task gets a git
  commit in its folder if that folder is a repo, so bad work can be reverted.
- New goals come from the Relay page or from an email (below).

### 3. Gmail channel (`channels/gmail.py`, stdlib `imaplib` + `smtplib` only)

Channels are one file each behind a small interface (`send`, `poll`), so
ntfy or Telegram can be added later as one new file plus one registry entry.

- **Out** (email to Emerson's own address, set in Relay settings): task
  started / finished / failed / parked, account switched, goal check
  passed, and a daily digest at a set time (default 17:00) of what got done,
  what is running, both meters, and anything waiting on him.
- **In**: polled every 2 minutes. Only mail that is **from his address and
  whose `Authentication-Results` header shows `dkim=pass` for gmail.com** is
  read; everything else is ignored and not answered. The first line must be
  one of a fixed set: `status`, `pause`, `resume`, `stop <task>`,
  `goal: <text>`, `task: <goal> <text>`, `digest`. Anything else gets a
  short "commands are ..." reply. Mail text is **never** run as a shell
  command. `goal:` and `task:` text becomes a file, which a session then
  works on with full permissions, so the sender check is the lock on the door.
- Replies stay in the same email thread (`In-Reply-To`).
- The app password is stored in a mode-600 file in the Relay data folder,
  entered on the Relay page, and never logged or shown again.

### 4. The Relay page (hub app)

Queue and goals with progress, what is running (account, effort, tokens,
last action, a live tail), both accounts' meters, pause/resume/stop buttons,
add goal and task forms, Gmail settings (address, app password, digest
time, a "send test email" button), and the event log. Mind the house
style: no white-on-white text, works fullscreen without the sidebar.

## Things to know

- **Cost**: every fresh session costs about 50k tokens to start once the
  prompt cache has gone cold (memory `crew-relaunch-cost`), so tasks should
  be meaty and launches few.
- **Terms**: Claude Code's headless mode is Anthropic's own feature. The
  consumer terms page (checked 2026-09-29 through a summarising fetch, not
  read in full) bans sharing accounts and automated access "except ...
  where we otherwise explicitly permit it"; nothing found against one
  person having two accounts. Expect weekly limits to be the real cap.
- **Crew Room's permission-mode question** (its `known_gaps`: auto vs
  bypass) is settled for Relay: bypass. Tell that session on the board.
- Fullscreen, no ALL-CAPS copy, one file per channel/room/strategy, and
