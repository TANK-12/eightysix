# Exo Lab: plan

date: 2026-10-08 · for: both (Emerson and Claude) · Relay task 102

Exo Lab is a Forge app that is half a real-world physics test bench for
exoskeletons, cybernetic limbs and mechs, and half a game about soldiers in
exo suits. This file is the plan; `../WIP.md` holds the live state.

   Eighty Six.

## 3. Architecture

```
apps/exolab/
  forge_app.json      Forge manifest (port 8466)
  web_app.py          FastAPI: static, /shared, /characters, the API
  exolab/             the engine-free core (Python)
    registry.py       loads data/*, validates, applies a profile (multipliers)
    vec.py            small rotation and vector helpers on numpy
    skeleton.py       reads a VRM's humanoid skeleton (rest pose, bone lengths)
    human.py          body segments (de Leva), shoulder girdle rhythm, ROM envelope, strength norms
    mechanisms/       one module per shoulder mechanism kind (registry by name)
    structure.py      beam sections, stress, deflection, safety factor, mass
    actuators.py      torque and speed limits, power, efficiency, battery
    arm.py            arm chain: exo fitting to the human arm, cuff springs, statics, inverse dynamics
    benches/          one module per test kind (registry by name)
    derive.py         game stats from the effective specs
    report.py         dated markdown report of a test run (docs library)
  data/
    materials/*.json  baseline values with sources
    actuators/*.json  joint drives (harmonic, planetary, cable, ball screw, hydraulic, spring)
    mechanisms/*.json shoulder mechanism presets (kind + geometry)
    models/*.json     exo_full, exo_lite, cyber_arm, cyber_leg, biped_mech, spider_mech
    human/*.json      segment table, ROM envelope, girdle rhythm, comfort limits
    tests/*.json      bench tests (kind + parameters + pass rules)
    motions/*.json    named arm motions (overhead reach, aim, throw...)
    game/*.json       abilities and modes for the game half
  profiles/           Emerson's edits: named sets of multipliers and overrides
  static/             web front end: home menu, tester, editor, game (three.js)
  tests/              pytest (core, API) + golden/ test vectors for ports
  docs/               this plan, PORTING.md, physics notes
~/Models/exolab/      Blender build scripts and .blend saves for fitted parts and mechs
```

**API** (all JSON):

- `GET /api/registry`: every material, actuator, mechanism, model, test,
  motion, character and ability, as summaries.
- `GET /api/model/{id}?profile=`: the effective model: resolved specs, masses,
  and the mechanism **layout** (pivots, axes, link segments) for drawing.
- `GET/PUT /api/profiles/{name}`, `POST /api/profiles/{name}/copy`: Emerson's
  edits. A profile holds multipliers and overrides only; baselines never change.
- `POST /api/run` `{model, test, profile, overrides}`: runs a bench test;
  returns verdicts, metrics, series for charts and frames for the 3D playback.
- `POST /api/pose` `{model, pose, payload}`: instant loads for one pose (the
  drag-the-arm mode).
- `GET /api/derive/{model}?profile=`: game stats.
- `POST /api/report`: saves a dated markdown report into
  `~/Forge/docs/library/exolab/`.

## 4. Physics: what the tester models, honestly

Every test page says what it models and what it leaves out. Numbers in `data/`
are typical handbook values with a `source` field; the UI calls them typical,
not certified.

**Relative specs.** Every numeric spec has a baseline (absolute SI value with a
source) and the active profile holds a multiplier (default 1.00). Effective
value = baseline × material multiplier × part multiplier. The editor shows the
multiplier (slider, log scale 0.1× to 10×, paired number field), the resulting
absolute value, and a "relative to" readout against a reference (steel for
metals and composites, nylon for plastics, the harmonic drive for actuators).
The four knobs Emerson named map like this:

| Knob | Materials | Parts | Actuators (joints) |
|---|---|---|---|
| Stiffness | Young's modulus E | section stiffness E·I | torsional stiffness |
| Strength | yield strength (and fatigue limit) | allowed stress | peak and continuous torque cap of the housing |
| Weight | density | mass | mass |
| Power | (none) | (none) | continuous and peak torque, speed, power |

Plus per-part choices: material, section size (tube diameter and wall), link
lengths, assist share, mechanism kind and its geometry.

**Human shoulder.** The arm pose is given as ISB humerus angles relative to the
thorax: plane of elevation φ (0 = sideways abduction, 90° = forward flexion),
elevation θ and axial rotation ψ. The shoulder girdle moves with it, which is
what makes exoskeleton shoulders hard:

- Scapulohumeral rhythm: the scapula rotates upward by
  `st = max(0, θ - onset) × slope` (defaults onset 30°, slope 0.4, so 60° of
  the 180° comes from the scapula; Inman 1944, the 2:1 rhythm).
- The clavicle elevates and protracts or retracts with the arm (defaults about
  20° elevation at full raise; protraction when reaching forward or across,
  retraction in abduction; after Ludewig 2009). On the model this is the VRM
  `shoulder` bone, so the shrug is visible.
- The glenohumeral (GH) joint centre therefore moves several centimetres
  during a full raise. It is the target the exoskeleton must follow.
- Range of motion: an envelope table (maximum elevation per plane, axial
  rotation range per elevation) from AAOS-style norms, editable.
- Segment masses and centres of mass from de Leva (1996), female and male
  tables; shoulder strength norms (isometric flexion and abduction torques)
  marked as approximate.

**Exo shoulder mechanisms** (registry, one module each):

1. `gimbal_lateral`: three motor axes meeting at a point fixed to the back
   frame, first axis sideways. Simple, but the axes line up (a singularity,
   gimbal lock) when the arm points straight out sideways, and its centre
   does not follow the girdle.
2. `gimbal_tilted`: the same with the first axis tilted up and back (default
   45°), which moves the singularity behind the head where arms rarely go
   (ARMin and Harmony use this trick).
3. `girdle_tracking`: the tilted gimbal on a two-joint passive girdle link
   (elevation and protraction), spring-balanced, so the centre follows the GH
   joint. The residual error is the force needed to drag the passive joints
   (friction plus unbalanced weight) divided by the cuff stiffness.
4. `soft_cable`: a cable exosuit with no rigid joint: no misalignment and no
   singularity, but it can only pull along its cable paths, so the assist
   depends on the pose.

Each mechanism can have a passive slider along the upper-arm link (absorbs
length mismatch).

**Fitting the exo arm to the human arm, per pose:** the exo upper-arm link
points at the human elbow; its roll and the exo elbow angle match the forearm.
Two cuffs (upper arm, forearm) join exo and arm through springs (normal
stiffness about 2-5 N/mm for strap plus soft tissue, lower along the limb).
The gap between where the arm is and where the exo holds the cuff gives the
**interaction force**, and force over strap area gives the **pressure** on the
skin, compared with comfort bands (4.3 kPa capillary closing pressure for all
day wear; about 8 and 16 kPa for short use and pain; marked approximate).

**Joint-level results:** exo joint angles against their limits; singularity
closeness `|det[a1 a2 a3]|` (1 = far, 0 = locked); the joint speed a motion
demands, `q̇ = J⁻¹ω`, against the actuator's top speed; the torque each motor
must give, `τ = Jᵀ M`, against its continuous and peak torque.

**Structure:** every link is a beam (tube or rectangle) of its material:
mass `ρ·A·L`, bending stress `M·c/I`, safety factor `yield / stress`, tip
deflection `F·L³ / (3·E·I)`; fatigue checked against the fatigue limit for
repeated tests. A part whose safety factor drops below 1 is drawn as broken.

**Dynamics:** motions are minimum-jerk paths between poses; inverse dynamics
(recursive Newton-Euler) on the arm plus exo plus payload gives torques,
power `τ·ω`, energy per cycle and battery endurance.

Not modelled (said on the page): soft tissue sliding in detail, muscle
forces, heat, wear, control-loop stability, impacts beyond a spring-damper
drop model.

## 5. Bench tests (real-world tester)

Each is a JSON file (kind + parameters + pass rules), run by its bench module:

| Test | What it answers |
|---|---|
| `shoulder_rom` | Sweep the whole human shoulder range: what share the exo can follow (no joint limit, no clash, no lock), worst misalignment, worst cuff force and pressure, closest approach to gimbal lock, a map over plane × elevation. |
| `shoulder_motions` | Named motions (overhead reach, sideways raise, reach across, reach behind back, rifle aim, throw) played in 3D with the GH centre, the exo centre, the misalignment line and cuff force arrows; charts per frame. |
| `shoulder_hold` | Hold a payload at standard poses (arm forward level, overhead, carry at the side): motor torque against capacity, what the human still carries, safety factors, sag at the hand. |
| `lift_cycle` | Lift a box from waist to overhead: peak torque, speed, power, energy per lift, lifts per battery charge. |
| `close_fit` (chunk 2) | Gap between the fitted shells and the moving skin through the motions: pinches, clashes between shells (pauldron against chest at high raise), worst gap. |
| Later chunks | Cyber limbs: grip, lift, range, socket load. Mechs: static stability margin, leg loads, gait, drop test. |

Results show as verdict cards (pass, warn, fail with the reason), charts, a
3D heat colour on the parts, and a comparison against the baseline profile
(arrows for better or worse). "Save report" writes a dated markdown file to
the docs library.

## 6. The editor (the "great editor")

- Tabs: **Materials**, **Joints** (actuators), **Parts**, **Mechanism**,
  **Human**, **Tests**.
- Simple mode: the four relative knobs per item (stiffness, strength, weight,
  power) as log sliders with number fields. Advanced mode: every absolute
  value, section sizes, axis angles, comfort limits, test parameters.
- A materials chart (stiffness per weight against strength per weight, an
  Ashby chart) showing each material, moving live as knobs change.
- Live re-run: change a knob, the current test re-runs (debounced) and the
  3D view and results update, with arrows against the baseline.
- Profiles: save, load, copy, compare A against B; undo and redo (the shared
  `forge_undo.js`); reset one item or all.
- Per-part table: mass, safety factor, deflection, motor load, sortable.

## 7. The game half

Soldiers in exo suits, after CoD Advanced Warfare's exo moves and Crysis's
nanosuit modes, with every number derived from the suit Emerson built in the
tester:

- Third person, the VRM soldier wearing the chosen suit (full or lite).
- Moves: boost jump (double jump), boost dash, ground slam, slide, sprint.
- Suit modes (Crysis style): Armour, Strength, Speed, Cloak, each draining
  the battery; energy bar regenerates.
- Derived stats: jump height and sprint speed from leg drive power and total
  mass, carry and throw limit from shoulder and elbow torque and link
  strength, armour from plate material and thickness, energy from battery
  capacity and motor efficiency. Overloading a part breaks it in the game too.
- First level: a test range (Poly Haven ground and props, sky) with an
  obstacle course, crates to lift and throw, targets and walls to punch, a
  timer. Later: drones and robots to fight, missions, a squad.

Fitted shells: in Blender, select the body faces a shell covers (by bone
weights and cut planes), offset outward by the fit gap, give them thickness,
bevel and panel lines, and export each shell as its own named object with its
bone recorded, so the front end attaches it to that bone. The fit gap and
shell thickness come from the model JSON, so the Blender script and the
physics read the same numbers.

## 9. Portability (Unity or Unreal later)

- Engine-free: `data/` (JSON), `exolab/` (Python core behind HTTP), the GLB
  and VRM assets, humanoid bone names, the test definitions.
- Per engine: the drawing and the game feel. A new engine front end either
  calls the local API, or ports the core module by module and checks itself
  against `tests/golden/*.json` (inputs and expected outputs saved by pytest).
- `docs/PORTING.md` (chunk 5) maps each piece to Unity (UniVRM, ArticulationBody,
  JSON) and Unreal (VRM4U, Chaos, JSON).

## 11. How each chunk is checked

- pytest for the core and the API (sweeps over many poses to catch the
  singular and edge cases: arm straight down, straight up, along an axis).
- black and pyright on every Python file touched.
- Headless Chrome screenshots of the home menu, the tester, the editor and
  the game (SwiftShader WebGL), looked at, not just taken.
- A critic agent on the plan, and on the diff before a chunk is called done.
