## HIGH
### N1. Motion edits are shown, accepted and saved, then ignored by the motions bench (CONFIRMED)
- benches/motions.py:33 reads `mo = reg.get("motions", mid)`, which is the raw data. The profile's overrides on motions never reach the run.
- The editor shows every motion's payload and key fields in the Tests tab whenever the motions test is open, without Advanced (editor.js:1150).
- API probe: inline override motions.throw `payload_kg=100`, then `keys.4.t=20`, then `keys.2.elev=180, keys.2.plane=-90`, each run with only=throw. Every result is identical to baseline: payload_kg 0.4, 31 frames, peak 327.2 W, warnings []. PUT /api/profiles/motion-edit with the same override returns 200.
- Chrome: setting "motions/throw: payload_kg" to 100 marks the row as edited, but all six cards stay identical and the throw card still reads "4 mm · 327 W". Shot: motions-payload-100-ignored.png.
- Fix: `mo = reg.effective("motions", mid, rig.profile)`. After that, also bound the run time; see N2.

### N2. M1 is not fixed: the allowed minimum steps still give a 17-20 s run, and over 30 s with the range widened (CONFIRMED)
- The WIP says "a run stays a few seconds". limits.json:77-78 lets plane_step and elev_step go down to 2, and shoulder_rom.py:23-24 sweeps every cell.
- exo_full, shoulder_rom, overrides plane_step=2 and elev_step=2: 10,556 cells. Server time was 19.7 s and 18.2 s in-process (load about 2), and 17.2 s over curl to uvicorn (load 9.6). exo_lite took 15.9 s.
- Adding human.rom `plane_deg.0=-180`, `plane_deg.8=180` and every `max_elevation_deg.*=180` (all allowed) gives 16,471 cells: 33.4 s on exo_full and 31.9 s on exo_lite.
- In Chrome, both step fields are visible without Advanced. Typing 2 and 2 gave the chip "pass · 58037 ms" while the machine was busy. /api/run is synchronous with no cancel, so every further edit queues another full sweep.
- After N1's fix, motions get the same problem. Six motions stretched to 20 s at 120 fps is 14,406 frames, and play plus check alone took 12.5 s in-process.
- Fix: cap the work, not each field. For example, refuse or clamp when planes × elevs × twists exceeds about 3000, and for motions and lift when end × fps exceeds about 1500 frames per motion. Or raise the step minimums to about 5.

## MED
### N3. Huge JSON integers give a 500 on every route that takes an inline profile (CONFIRMED)
- Probe: a raw body with a 401-digit integer as a knob, e.g. `{"model":"exo_full","test":"shoulder_hold","profile":{"knobs":{"materials":{"pa12":{"stiffness":1000…0}}}}}`.
- Result: 500 "Internal Server Error" on /api/run, /api/model, /api/pose, /api/derive and /api/report. The same integer as an override value (cuffs.0.width_mm) also gives 500. PUT returns 400 "OverflowError: int too large to convert to float".
- Causes: clamp_knob (registry.py:230) catches only TypeError and ValueError; `math.isfinite(value)` (registry.py:210) raises OverflowError on a huge int; `_profile` cleans inline profiles outside `_call` (web_app.py:92-97).
- Fix: refuse ints with abs > 1e308 as "must be a number", and run the dict branch of `_profile` inside `_call`.

### N4. Text in the four "auto" (null) length fields bypasses limits.json (CONFIRMED)
- registry.py:200-202 accepts any string when the baseline is null. The affected fields are models/*/links.{2,3}.length_m on exo_full and links.{1,2} on exo_lite. parts.py then calls `float(...)` on the string.
- `links.3.length_m="-5"` returns run 200 with a fail verdict computed on a -5 m forearm strut. `" 2 "` gives a 2 m strut, past the 1.5 m maximum.
- `"nan"` or `"inf"` returns /api/model 200 with `total_kg: null` (148 nulls in the response), while /api/run returns 400 "cannot convert float NaN to integer".
- `"1e300"` returns /api/model 500, because `_pose_frame` in `_model_json` is not wrapped in `_call` (web_app.py:296).
- PUT saves `"nan"` with 200. After that, GET /api/derive?profile=autotext returns 200 with nulls.
- The editor itself only sends numbers, so this needs the raw API or a hand edit.
- Fix: for a null baseline, accept None or a number checked by limit(), and wrap `_pose_frame` in `_call`.

### N5. Motion times squeezed to nearly zero (inside [0, 20]) give NaN and inf results, shown as nulls, "nan" text and a false "no draw" (CONFIRMED, reachable in the UI)
- Probe: set tests.lift_cycle `params.keys.1.t`, `.2.t` and `.3.t` to 1e-300 in the Tests tab of the open test (no Advanced needed).
- Result: 200, verdict fail, and 40 nulls (energy_per_lift_j, frames[0].torques.J1 and others).
- The energy card reads "nan J … mean nan W" and is marked pass.
- The "Lifts per charge" card says "no draw: no powered arm drive takes power from the battery", which is wrong.
- The lift card reads "J1 needs 2293021184958695…(a 300-digit number).0 rad/s".
- The tiles read "Hardest motor –", "Strap pressure – kPa" and "Weakest strut safety 999.0". Shot: lift-keys-1e-300.png.
- With the times at 1e-10 s, the energy card reads "2379277294050227098646100706219054333952 J".
- Causes: benches/__init__.py:401 divides by `(span/2)**2`, which becomes 0 for spans under about 1e-154. lift.py:45 reads NaN energy as "no draw".
- Fix: require a motion of at least about 0.1 s (or floor the span at 1/fps in play), and check results with math.isfinite.

### N6. A hand-edited or odd profile file gives a 500, and so does the page once that profile is loaded (CONFIRMED)
- A file containing `[1,2]` or `null`: GET /api/profiles/x, run by name and copy all return 500. load_profile calls `prof.setdefault` on a non-dict (registry.py:300).
- Files containing `{"knobs":"x"}`, `{"knobs":{"materials":5}}` or `{"knobs":{"materials":{"pa12":5}}}`: running by name works and returns warnings. But an inline profile with the same name returns 500, because `edits_of(_saved(name))` (web_app.py:95) calls `.items()` on the raw file (registry.py:344). That inline profile is exactly what the page sends for every live run after loading.
- Related: a saved file holding a value the new checks refuse (e.g. `cuffs.0.width_mm: 0`) is labelled "handbad (unsaved edits)" on an unchanged run. No real profiles exist yet; ~/ForgeGameData/exolab/profiles is absent.
- Fix: in load_profile, refuse a file that is not a dict with a ValueError. In `_profile`, compare against `clean_profile(name, _saved(name), REG)[0]`.

### N7. A gearbox limit ("slips at", torque_limit_nm) of exactly 0 means no limit at all (CONFIRMED, API only)
- parts.py:177: `peak = min(peak, limit) if limit > 0 else peak`. limits.json allows 0.
- POST /api/model, J1 (cont, peak) on harmonic_m by torque_limit_nm:

  | torque_limit_nm | J1 (cont, peak) | with power ×20 |
  |---|---|---|
  | 0 | (30, 60) | (600, 1200) |
  | 0.001 | (0, 0) | (0, 0) |
  | 1 | (1, 1) | (1, 1) |

- The hold verdict is warn at 0 and fail at 0.001. Today only the API reaches this: the field is derived, so the editor does not list it.
- Fix: treat the limit as "no limit" only when the field is absent, or make the limits.json minimum above 0.
